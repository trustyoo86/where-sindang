# 1. 인증·저장 스택: Auth.js + Neon, 유저 테이블 없음

날짜: 2026-06-16

## 상태

채택(Accepted)

## 맥락

어디가신당은 지금까지 백엔드·DB·유저 개념이 없는 정적 콘텐츠 큐레이션 앱이었다. 모든 방문자는 익명 Reader다.

가벼운 SNS 로그인을 도입한다. 로그인의 유일한 목적은 **찜**(User가 Place를 저장)이며, 그 가치는 **기기 간 동기화·영구 저장**이다. 공급자는 **카카오 + 구글**. 국내 타깃이라 카카오가 필수다.

요구를 정리하면: OAuth(카카오·구글) + User에 귀속된 찜의 영속 저장 + "가벼움". 정적 Next(App Router) / Vercel 환경.

## 결정

**Auth.js v5 + Neon Postgres**를 쓴다.

- 인증: Auth.js v5. 카카오·구글 provider 내장. **세션은 JWT 쿠키, DB 어댑터 없음.**
- 저장: Neon 서버리스 Postgres + 생SQL. 테이블 단 하나 `saved_places(user_key, place_slug, created_at)`.
- 신원: `user_key = "provider:providerAccountId"`. 별도 users/accounts 테이블 없음.
- 프로필(이름·아바타)은 세션 토큰에서만 읽어 UI에 표시하고, DB에는 어떤 PII도 저장하지 않는다.

## 대안

### Supabase (Auth + Postgres + RLS, 통합)
정적 Next에 붙이기 가장 단순하고 구글은 토글로 켜진다. 그러나 **카카오는 토글 provider가 아니라 커스텀 OIDC/OAuth 수동 등록**이 필요하다. 카카오가 필수 요건이므로 가장 매끄러워야 할 부분이 가장 까다로워진다. 통합 단순함을 카카오 연동 매끄러움과 맞바꾸는 셈 → 카카오 우선으로 기각.

### Firebase (Auth + Firestore)
구글은 쉬우나 **카카오는 커스텀 토큰이 필요**해 통합이 아프다. 카카오 요건과 정면충돌 → 기각.

### Clerk 등 매니지드 Auth
구글은 쉬우나 카카오 연동이 까다롭거나 상위 요금제 필요. 기각.

### Auth.js + DB 어댑터(users/accounts 테이블)
프로필 영속화·공급자 간 계정 연결이 가능해지나 테이블 3~4개와 어댑터가 추가된다. 찜만 하는 현 범위엔 과하다. 나중에 작성·프로필 기능이 생기면 그때 어댑터를 더해 이행할 수 있다.

## 결과

**좋은 점**
- 부품 최소: provider 코드 + 테이블 1개. 가장 가벼운 경로.
- 카카오 연동이 Auth.js 내장 provider로 매끄럽다.
- DB에 PII가 없어 개인정보 수집이 최소다.
- 정적/SSG 페이지 대부분을 그대로 유지하고, 찜 상태만 클라이언트에서 하이드레이션한다.

**대가 / 주의**
- 공급자 간 계정 연결이 없다: 같은 사람이 구글·카카오로 각각 로그인하면 **서로 다른 User 둘**, 찜도 따로다. (도메인 결정으로 수용 — `CONTEXT.md` 참조)
- 유저 레코드가 없으므로 "계정 삭제 시 찜 정리" 같은 처리는 `user_key` 기준으로 직접 해야 한다.
- 프로필·작성·반응 등 기능이 늘면 Auth.js DB 어댑터 도입(이행)이 필요해질 수 있다.

## 미해결(구현 시 결정)

JWT 만료 기간, 정적 페이지에서 찜 상태 하이드레이션 방식(`/api/saved` 클라 fetch), 카카오·구글 redirect URI 및 env 등록.
